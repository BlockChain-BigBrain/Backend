# 블록체인과 DB의 역할 및 완료 기준

## 역할

- 백엔드: AI 결과 검증, 검증용 서비스 키로 EIP-712 서명 발급, 사용자 지갑이 전송할 calldata 생성, 온체인 결과 검증과 DB 동기화.
- 사용자 지갑: 등록·가격 설정·구매·출금 트랜잭션 승인과 전송. 사용자 개인키는 백엔드에 전달하지 않는다.
- 컨트랙트: 검증 서명·nonce·만료·등록자·지분·결제 금액 확인, 라이선스 발급, 수익 배분과 출금 집행.
- DB: AI 결과·업무 요청의 원본과 온체인 거래 결과의 조회용 기록을 저장한다. 트랜잭션 전송용 payload 생성만으로 완료 상태를 기록하지 않는다.

현재 실제 RPC 연동은 Hardhat 31337 / ETH / COMMERCIAL에 한정된다. AI 및 IPFS 실제 provider는 별도 연결이 필요하며, mock 결과로 실제 등록·구매 완료를 만들지 않는다.

## 완료 처리

등록과 구매·출금의 confirm API 및 이벤트 동기화 워커는 성공 영수증, 설정한 confirmation 수, canonical 블록, 대상 컨트랙트, 거래 발신자, calldata와 관련 이벤트를 확인한다. 확인 전 요청은 PENDING 또는 PREPARING 상태다. confirm API는 사용자 입력 txHash를 성공 증명으로 신뢰하지 않으며 RPC에서 다시 조회한다.

등록은 실제 calldata의 nonce로 서명 요청을 찾는다. 만료 전에 채굴된 거래는 동기화 시점에 서명 유효기간이 지났거나 새로운 서명 요청이 있어도 반영할 수 있다. 완료된 등록 요청을 조회 시 우선하고 대체된 미완료 요청은 SUPERSEDED로 처리한다.

구매 검증 시 NFT 잔액과 기여자 지분은 거래가 채굴된 블록을 기준으로 조회한다. 실제 ETH 지갑 구매는 DB 취소로 중단할 수 없으므로 취소 API에서 거부한다. 지갑에서 전송을 취소하거나 실패했다고 판단한 UI 상태와, 온체인 구매 완료 여부는 별개다.

수익 배분 기록은 출금 완료 기록과 구분한다. withdrawRevenue는 실행 시점의 전체 잔액을 출금한다. 따라서 준비 시점 이후 수익이 늘어도 실제 RevenueWithdrawn 금액을 검증하여 DB에 저장한다. 출금 요청과 지갑 주소는 하나의 DB 트랜잭션에서 저장하고 같은 요청의 지갑을 나중에 바꾸지 않는다.

가격의 DB 반영과 판매 활성화 검사는 필요한 confirmation을 지난 블록의 가격만 사용한다. 과거 이벤트 재처리 시에도 가장 최근의 확인된 체인 가격을 읽어 오래된 값으로 되돌리지 않는다.

## 장애 복구

BlockchainEvent의 chainId + transactionHash + logIndex 유니크 키와 구매·배분 원장의 유니크 제약, DB 행 잠금으로 재처리에 따른 중복 생성을 방지한다. 이벤트 처리와 처리 완료 표시 사이에 장애가 나도 같은 영수증을 재검증하여 복구한다.

스캔 중 실패한 거래의 재시도 이벤트가 DB에 저장되지 않았다면 커서를 전진시키지 않는다. DB에 남은 미처리 이벤트는 다음 폴링에서 재시도하므로, 사용자 요청과 연결되지 않는 외부 거래는 재시도 원장에 남기면서 다른 거래의 동기화를 진행할 수 있다. 낮은 재시도 횟수를 우선하여 실패가 반복되는 거래가 다른 재시도를 독점하지 않도록 한다.

블록 범위는 블록·트랜잭션·로그 순으로 처리하고 범위 끝 블록 해시를 스캔 전후 비교한다. 커서 또는 저장된 이벤트의 블록 해시 불일치, 스캔 도중 체인 변경을 감지하면 추가 처리를 중지한다. 이는 자동 금융 롤백이 아니다. 재구성 이후 이미 반영된 기록은 운영자가 canonical 체인과 대조해 복구하고 워커를 재시작해야 한다.

운영 중에는 미처리 이벤트의 error/attempts와 커서 지연, blockchain health의 blockedReason을 감시해야 한다. 현재 컨트랙트는 backend request ID를 이벤트에 포함하지 않으므로 백엔드 요청 없이 직접 실행한 거래는 자동 사용자 매핑이 제한된다.
